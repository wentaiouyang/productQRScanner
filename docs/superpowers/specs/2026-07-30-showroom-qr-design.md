## 0. 本次修订说明

第一版把这件事理解成「扫码看产品信息」。业务 brief 显示真实目标大得多——客户和 trade 边逛展厅边扫码**建立购物车**、查安装与规格指南、浏览已安装的完整系列、生成**能直连内部系统的采购单并快速收款**；同时明确要用**电子货架标签（ESL）** 取代纸质标签。

这已经不是一个项目，而是一个需要分期的计划。本版做三件事：把 brief 的每项能力对照数据可达性逐条评估、指出三个硬约束、给出分期方案。

**第一版仍然有效的部分**：gateway 调用契约、字段映射、可见性规则、客户页设计。它们成为 Phase 1，见第 7 节和 README。

## 1. 目标与核心问题

**目标**（brief 原文提炼）：提升客户体验——让客户和 trade 扫描展厅每件所需产品来建立购物车，查看安装与规格指南，浏览已安装的完整系列以更有效利用时间；提供实时价格与库存；并能生成直连内部系统的采购单，给出指引并快速收款。

**核心问题**：

- 客户想快进快出，却必须停下来找人问——数字标签让客户可以自给自足，**trade 客户尤其需要**
- 员工时间成本与印刷成本
- 标签被拿走、损坏、或信息过期，需要反复更换
- 信息不在一处——stock、website、Mintsoft 各自一份
- 展厅员工被打断，或在两组客户之间分身
- 促销期收益最明显

**运营目标归属**：Innovative tech to service customers · Knowledge database prioritisation · Tiles revenue equals tapware

## 3. 约束 1：购物车、采购单、收款都需要写权限，而 app 现在一条都没有

gateway 文档对此毫不含糊：Entra app 能到达的**只有 4 个接口，全部只读**，并且明确写着 *"no write route allows `entraUser`"*。83 个接口里 `entraUser` 能到 4 个。

所以「加入购物车」「生成采购单」「收款」不是前端工作量的问题，**是权限和后端的问题**，属于需要技术团队开发的 Type 2/3 请求。这三项决定了 Phase 4 的排期，不该和 Phase 1 混在一起估算。

**但有一个不需要写权限就能落地的中间方案**，我建议 Phase 2 采用：

> **客户端购物车 + 交接码。** 扫码后「加入清单」只写进客户手机的 localStorage，不碰任何后端。逛完之后页面生成一个包含全部 SKU 与数量的**交接码**（一个二维码或短码）。客户走到柜台，员工扫这个码，在自己有写权限的系统（AOS/Tyche）里一次性建单。

这个方案立刻解决 brief 里最核心的两条——「客户可以自助」和「员工不必在两组客户之间被打断」——而且完全不需要等权限批复。客户体验上唯一的损失是不能自己在线支付，而支付本来就在更后面的阶段。

## 4. 约束 2：ESL 是硬件采购，而且现在这张卡片设计装不进去

brief 的「BENEFITS OF THE ELECTRIC SHELF LABEL」是整份文档里最具体的一节，但它是**采购决策而不是软件工作**。主流 ESL（SoluM、Hanshow、Pricer/VusionGroup 等）自带网关和推送 API，集成工作是「把产品数据推给厂商 API」，而这依赖先选型。

**必须提前说清楚的一点**：典型 ESL 是 2.6"–7.5" 的电子纸，单色或仅支持有限的几种颜色。我上一轮做的卡片版式——大号高对比衬线价格、9 个彩色表面处理圆点、占卡片六分之一的二维码——**在 2.6" 单色标签上既放不下也显示不出来**。要接近那个观感，至少需要 7.5" 以上的彩色电子纸，甚至 9.7"。

也就是说：**先定 ESL 型号和尺寸，卡片版式才能定稿。** 现在的版式是为纸质卡片和大尺寸彩色电子纸设计的。

顺带说明，brief 里「Ability to update when website is updated」这条收益，在「二维码 → 网页」这条路上**已经成立了**——网页每次访问都实时查 gateway。ESL 要做到同样的即时性，取决于厂商推送链路的延迟和推送频率配额。

## 5. 与已交付内容的冲突：纸质卡片

必须直接指出：ESL 收益列表里的第 2、4、5 条分别是「消除印刷成本」「防水」「标签常被小孩从亚克力卡座里拿走」——**我上一轮交付的纸质展厅卡片，正是这份 brief 想要取代的东西。**

我不建议丢掉它，但要重新定位：

- **纸质卡片 = 过渡与降级方案**，不是终态。用于 ESL 采购到货前的现在、断网或 ESL 故障时、以及临时上架的新品/样品。
- 因此**不该按终态继续投入**。目前的完成度（两种版式、可打印、可选产品）已经够用了，不要再加功能。
- 已建立的**设计语言**（三种字体角色、只有色点有颜色、发丝线层次）会延续到 ESL 和网页，这部分投入不浪费。

## 6. 分期方案

| 期 | 交付 | 依赖 / 阻塞 |
|---|---|---|
| **Phase 1** — 扫码看产品页 | 客户扫码即看到图片、规格、价格、库存、资料下载、同系列颜色、必配产品；员工登录后看成本与毛利 | **阻塞**：应用身份凭证（客户匿名访问）+ `products.read` 分配给部门安全组。详见第 8 节 |
| **Phase 2** — 自助建单 | 客户端购物车 + 柜台交接码（第 3 节方案）。这一期兑现 brief 的核心价值 | 无新权限依赖。需要和展厅确定柜台交接流程 |
| **Phase 3** — ESL 试点 | 单个展厅、单个品类的小规模试点 | ESL 选型与采购（Marketing/采购）；厂商 API 集成；卡片版式按屏幕尺寸重做 |
| **Phase 4** — 写入集成 | 真正的购物车落库、采购单直连 AOS/BC、线上收款 | gateway 写权限（Type 2/3，需技术团队开发）；支付方案；财务与合规审核 |
| **Phase 5** — 探索 | Chat Bot、AR 实景预览、PALS 关联推荐、RFID | 前四期稳定之后再评估 |

**Phase 1 和 Phase 2 可以并行推进**，因为 Phase 2 不依赖任何新权限。在等 Phase 1 权限批复的时间里把 Phase 2 做掉，是当前最有效的排期。

## 9. 需要决定的事

1. **RFID 要解决什么问题？** brief 提到「RFID labels behind each product display」，但二维码已经能唯一标识产品。如果目的是员工盘点或防盗，那是一条独立的硬件线；如果只是为了识别产品，它和二维码重复且更贵。目的不明确的话不建议现在投入。
2. **ESL 尺寸与型号**——这个决定之后卡片/标签版式才能定稿（约束 2）。
3. **柜台交接流程**——Phase 2 的交接码由谁扫、扫进哪个系统（AOS 还是 Tyche）、员工侧需要什么界面。
4. **瓷砖按平方米计价**（见第 10 节），需要确认价格展示与数量换算规则。
5. **部门安全组名称**——提权限申请必需，仍然缺。

## 10. 一个具体发现：瓷砖需要单独的价格模型

运营目标里有一条「Tiles revenue equals tapware」。我在真实产品记录里看到这个字段：

```json
"tileAndFlooringDimensions": { "uom": "", "sqmForUom": "", "dimensions": { "height": "", "width": "" } }
```

**瓷砖是按平方米计价的**，而现在的产品页和卡片都假设按件计价（`regularPrice` 直接当单价显示）。如果不处理，瓷砖在这个平台上会显示出错误或无意义的价格——那条运营目标就落不了地。

需要的是：瓷砖品类识别、按 `uom`/`sqmForUom` 的价格换算、以及「所需面积 → 件数 → 总价」的换算（这对 Phase 2 的购物车尤其重要，因为客户会按房间面积买砖）。这一项应该在 Phase 2 里单列，不要混进通用产品页。

## 11. 风险

1. **写权限决定了 brief 里最有价值的那部分能不能做。** 缓解：Phase 2 的客户端购物车方案先把大部分体验价值兑现，不等权限。
2. **ESL 是硬件，工期不由软件控制。** 缓解：Phase 1/2 走网页路线先上线，ESL 作为独立试点推进；二维码内容不变，ESL 到货不需要重做。
3. **视觉资产是这个平台最容易被低估的成本。** 「Visuals of installed products including swap outs and sizing」意味着大量拍摄/渲染与持续维护，工作量可能超过软件本身。缓解：Phase 3 之前先做一个品类的样板，用真实成本推算规模。
4. **字段结构与文档不一致。** gateway 自己的文档声明 `swagger.json` 有两处错误，要求以真实记录为准。缓解：契约测试锁定本应用依赖的字段。
5. **6–12 个月的跨度里 gateway 可能变化。** 缓解：所有 gateway 访问集中在一个模块，配合契约测试。
